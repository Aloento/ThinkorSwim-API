## 1. 项目定位

这是一个 **thinkorswim 网页版（TOSWeb）私有 WebSocket API（"wsjson"）的非官方客户端**，
不是 Schwab 官方 REST API。它通过模拟网页前端的 WebSocket 协议，实现：

- 认证（access token / 一次性 authCode 两种方式）
- 行情（股票报价、期权链、期权报价、市场深度、K 线）
- 账户（持仓、working orders、user properties、watchlist）
- 交易（下单、改单、撤单、订单事件流）
- 告警（创建、取消、查询、订阅）

另附带一个 **本地代理服务器（WsJsonServer）**，把上述能力再暴露为一个本地
WebSocket RPC，供浏览器/其他语言的客户端间接使用。

## 3. 核心运行时机制

### 3.1 连接与状态机（realWsJsonClient.ts）

- `ChannelState`: DISCONNECTED → CONNECTING → CONNECTED / ERROR。
- 构造函数默认直接创建 `WebSocket("wss://thinkorswim-services.schwab.com/Services/WsJson")`，
  并伪造浏览器请求头（`Origin: https://trade.thinkorswim.com` 等）。
- 连接建立后发送握手：`{ver:"27.*.*", fmt:"json-patches-structured", heartbeat:"2s"}`。
- 收到 connectionResponse（含 `session/build/ver`）后自动发 `login` 或 `login/schwab`。
- 登录成功 → CONNECTED，resolve `authenticateWithAccessToken/withAuthCode`。

### 3.2 消息回路

```
socket.onmessage
  → JSON.parse
  → 是 connectionResponse? → 发登录
  → 是 login / login/schwab?  → 状态机流转 + resolve
  → 否则 → ResponseParser → GenericIncomingMessageHandler
       snapshot: 直接以 body 覆盖 store[service_id_ver]
       patch:    fast-json-patch 增量合并到 store[service_id_ver]
  → 每个条目 {service, body} 推入 BufferedIterator
  → MulticastIterator 多播 → 各 dispatch 处按 service 名过滤
```

关键点：

1. **响应只按 `service` 名路由，不按请求 `id` 关联**——同类请求并发时消息会串台。
2. `GenericIncomingMessageHandler.dataStore` 以 `service_id_ver` 为键无限增长，无淘汰。
3. 心跳消息（`{heartbeat: n}`）会被忽略，**客户端从不回心跳，也没有断线重连**。

### 3.3 请求分发（Observable 模型）

使用 `obgen` 库：`dispatch()` 发送请求后返回 `deferredWrap(iterator).filter(service)`，
对外表现为 `AsyncIterable`（流式：quotes/chart/marketDepth…）或 `.promise()`（一次性：
search/watchlist/userProperties…）。

### 3.4 认证链路（两条）

| 路径          | 输入                                 | 服务                                                                                                          | 输出                                                 |
| ------------- | ------------------------------------ | ------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------- |
| token 登录    | accessToken(+refreshToken)           | `login`（params: token/domain=TOS/platform=PROD/tag=TOSWeb）                                                  | 复用同一 token，`authenticationStatus==="OK"` 即成功 |
| authCode 登录 | 一次性 authCode（浏览器 OAuth 抓取） | `login/schwab`（params: authCode/clientId=TOSWeb/redirectUri=https://trade.thinkorswim.com/oauth/tag=TOSWeb） | 返回新 `token` + `accessTokenInfo.refreshToken`      |

`example/browserOauth.ts` 用 puppeteer-extra + stealth 打开 trade.thinkorswim.com，
在 `sws-gateway-nr.thinkorswim.com` iframe 里定位 `#loginIdInput / #continueBtn / #passwordInput`
输入账密，拦截回跳 `trade.thinkorswim.com/oauth?code=...` 的请求并 abort，取出 code。

README 记载：token 有效期 24 小时；authCode 一次性。
**代码中 refreshToken 只是被保存，从未用于刷新 token**（没有刷新实现）。

### 3.5 下单流程（两段式）

1. `placeOrder()`：先发 `place_order`（ver 1，`action: "CONFIRM"`，requestType `INIT_STOCK`）
   得到订单草稿/确认信息；
2. 再发 `place_order`（ver 0，`action: "SUBMIT"`，requestType `EDIT_ORDER`）真正提交；
   改单 `replaceOrder()` 复用 SUBMIT + `refOrderId`。
3. 撤单走独立服务 `cancel_order`；成交/状态推进通过 `order_events` 推送。

⚠️ 细节缺陷见 [03-问题与风险清单](03-问题与风险清单.md) 第 4 节（SubmitOrder handler 的
service 被标为 `"unused"`，导致 placeOrder 返回的 promise 实际无法按预期 resolve）。

## 4. 工程化与依赖

- **构建**：`tsc`（nodenext/ESM，strict），产物 `dist/`；`esbuild` 打包脚本指向
  `dist/client/tdaWsJsonClient.js` —— **该文件不存在，bundle 脚本已失效**。
- **测试**：jest 30 + babel-jest + jest-websocket-mock，仅 1 个测试文件 2 个用例。
- **CI**：GitHub Actions，Node 24/25，跑 `prettier --check + build + eslint + jest`。
- **运行时依赖（重要）**：`puppeteer ^24` 竟然在 `dependencies`（下载 Chromium，极重，
  且只有示例用）；`prompts`、`resolve` 疑似未使用；`lodash-es` 仅用了 `isString`。
- **package 出口**：`main: dist/web.bundle.js`、`types: dist/web.d.ts` —— tsc 并不产出
  这两个文件，**发包配置与实际产物不符**（exports "." 是正确的 dist/index.js）。
- **仓库卫生**：根目录提交了 `cert.pem` / `key.pem`（自签测试证书也应移出仓库）；
  `src/client/types/orderEventTypes.ts` 为空文件；README 的 import 示例拼错包名（toa-）。
- Node 环境：CI 为 24/25；本机 Node v26.10（需验证兼容基线）。
