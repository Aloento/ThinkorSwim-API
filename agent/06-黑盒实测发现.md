# 06 · 黑盒实测发现（2026-10-13，guest/PaperMoney 会话）

> 本文只记录**线上实测证据**（工具与原始帧见文末清单），推翻/确证旧假设。
> 所有测试均连 `wss://papermoney-services.schwab.com/Services/WsJson`，零真实资金流量。

## 1. 认证链（已彻底打通，工具 auth-guest.mjs）

真实前端流程（CDP 完整抓帧证据 `watch2-console.txt`）：

```
1. GET  https://trade.thinkorswim.com/guestpass → 302 sws-gateway 登录 iframe
2. POST https://sws-gateway.thinkorswim.com/api/v2/auth/login   (clientId=TOSGuestPassWeb)
3. POST https://sws-gateway.thinkorswim.com/api/v2/auth/assert  (password method，无 MFA)
4. 302 https://trade.thinkorswim.com/oauth?code=X&session=…
5. POST https://tosweb-sm.thinkorswim.com/api/v1/tsm/authorize  {authCode:X, clientId}
   → 201 {authCode:Y, eat, newT, newTExpireTime…}   ← Y 才是 wsjson 用的 code
6. WS  wss://papermoney-services.schwab.com/Services/WsJson
     握手 → login/schwab {authCode:Y, clientId, redirectUri, tag:"TOSWeb"}
     → snapshot {authenticationStatus:"OK", token, accessTokenInfo.refreshToken, …}
7. 前端把 token 写入顶层 frame sessionStorage.token（wsjson 之后可复用）
```

关键结论：

| # | 发现 | 证据 |
|---|---|---|
| F1 | **数据中心端点分离**：PaperMoney 必须连 `papermoney-services.schwab.com`；paper token 拿到 `thinkorswim-services` 用会报 `Invalid token (server session id)` | probe v3/v5 对照实验 |
| F2 | **token 可跨 WS 连接复用**（新连接直接 `login` 成功），无需 Cookie；有效期约 24h（newTExpireTime - 当前 ≈ 23.9h） | `auth-guest.mjs` 验证 + tsm 响应 |
| F3 | oauth 原始 code 会被前端 `tsm/authorize` 消费；**wsjson 需要的是 authorize 返回的新 authCode**——上游库用旧 code 直发 login/schwab 已不可行 | `watch2` 帧序列 |
| F4 | guest 会话无 MFA；`login/schwab` 响应**结构未漂移**：`accessTokenInfo.refreshToken` 仍在（login-raw.json / watch2） | `login-schwab-raw.json` |
| F5 | `login` 响应新增 `isCryptoSignupEligible`、`isPdtHidden` 权限位；`quotePermissions` 从对象变为**数组**（旧类型定义仍按对象处理需注意）；`userDomain` 仍返回 "TDA"（遗留字段） | `login-raw.json` |
| F6 | guest 账号结构：`accounts` 返回 `code: "D-12345678"`（margin）+ `D-23456789`；`statement` 用 `account:"COMBINED ACCOUNT"` 即可 | accounts/statement 帧 |

## 3. 写操作（W 组，全部模拟盘，write-2026-10-13/*.jsonl）

| 用例 | 结果 | 关键发现 |
|---|---|---|
| W1 CONFIRM | ✅ | 草稿 snapshot `{groupType, orders[], maxOrders}`；orderId=0 占位；价格经 patch 注入（natPrice/bidPrice/askPrice/stopPrice）；服务端自动把 limitPrice 对齐到 mid（我们传 $1 被改 340.95——**服务端有权改写草稿价**） |
| W2 SUBMIT | ✅ | **SUBMIT 必须复用 CONFIRM 的草稿 id**（`update-draft-order-AAPL`）。换 id 报错 `"Can not submit while prices are not available!"` 并回 `unsubscribe/place_order$<id>` 快照帧；orderId=5411072868 经 **patch `/orders/0/orderId`** 返回（不是独立响应体） |
| W4 cancel | ✅ | snapshot `{result:"Cancel order for #… was sent"}`；重复撤单 → **error 帧** `"has already been cancelled or is in a final state"`（isTerminal:true） |
| W6 alerts | ✅ | create→snapshot 含完整 alert（id=25611753, version, status:ACTIVE）；lookup 返回 alerts[]；cancel→`{alertId, result:"Alert cancelled"}` |
| 错误帧机制 | ✅ | `header.type:"error"` + `body:{message, isTerminal}` 全局一致；错误后服务端常伴 `unsubscribe/<service>$<requestId>` 快照帧 |

补充实测：响应条目 header.id 与请求 id **原样回带** → **id 路由完全可行**（task-1 的依据）。

## 5. 对旧代码/旧文档的推翻

- 01/02 号文档中"两段式下单 ver 1→ver 0"描述不准确：实测 CONFIRM 用 ver:1、SUBMIT 用 ver:0 且**同 id**；真实差异在 `action` 与 requestType。
- README "TDA 老通道"实际仍在响应字段里（userDomain:"TDA"），但认证入口已完全是 Schwab OAuth。
- `unsubscribe` 是独立服务名（推送 `service$id`），做资源清理时可用。
