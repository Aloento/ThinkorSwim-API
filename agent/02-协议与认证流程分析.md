# 02 · wsjson 协议与认证流程分析

> 依据：通读 `src/client/**` 全部 handler + 2026-10-13 匿名线上探针（见 [00-基线验证记录](00-基线验证记录.md)）。
> 本篇是"协议文档"：把散落在代码里的隐性知识固化下来，作为黑盒测试与重构的基准。

## 1. 传输层

- 端点：`wss://thinkorswim-services.schwab.com/Services/WsJson`
- 必须请求头（伪造浏览器环境）：
  `Origin: https://trade.thinkorswim.com`、`Pragma/Cache-Control: no-cache`、
  `Connection: Upgrade`、`Upgrade: websocket`、`Sec-WebSocket-Version: 13`、
  `Sec-WebSocket-Extensions: permessage-deflate; client_max_window_bits`
- **permessage-deflate 必须开启**（实测关闭会被 1006 踢掉）。
- 帧内全部为 JSON 文本帧。

## 2. 会话生命周期

```
connect ──▶ 发 {ver:"27.*.*", fmt:"json-patches-structured", heartbeat:"2s"}
      ◀── {session, build, ver}                 # connectionResponse
      ◀── {"heartbeat":2000} 每 2s              # 服务器单向心跳，客户端无需回复
发 login / login/schwab
      ◀── payload[0].body = 登录响应             # 成功后才允许发业务请求
业务请求 payload[…]
      ◀── payload[…] (snapshot | patch)         # 可能持续推送
```

实测（2026-10-13）：`build` 已是 `27.2640.4-Q3`（仓库 fixture 仍是 `27.2323.3-B0`）。

## 3. 消息信封

请求：

```jsonc
{ "payload": [ { "header": { "service": "...", "id": "...", "ver": 0 },
                 "params": { ... } } ] }
```

响应条目：

```jsonc
{ "payload": [ { "header": { "service": "...", "id": "...", "ver": 0,
                             "type": "snapshot" | "patch" },
                 "body": { ... } } ] }
```

- `type: "snapshot"`：body 是该 (service,id,ver) 流的完整状态。
- `type: "patch"`：body = `{ patches: [RFC6902 JSON Patch…] }`，需对同一
  `service_id_ver` 的既有状态做增量合并（`fast-json-patch.applyPatch`）。
- 心跳 `{"heartbeat":n}`、connectionResponse 不带 payload。
- **路由只按 service 名**：`dispatch()` 用 `filter(msg => msg.service === handler.service)`；
  请求 header.id 并未参与响应关联（风险见 03 §3）。

## 4. 认证（核心链路）

### 4.1 两种方式

|          | A. token 登录                                          | B. authCode 登录                                                                                 |
| -------- | ------------------------------------------------------ | ------------------------------------------------------------------------------------------------ |
| 服务名   | `login`                                                | `login/schwab`                                                                                   |
| params   | `{token, domain:"TOS", platform:"PROD", tag:"TOSWeb"}` | `{authCode, clientId:"TOSWeb", redirectUri:"https://trade.thinkorswim.com/oauth", tag:"TOSWeb"}` |
| 成功判据 | `authenticationStatus === "OK"`                        | `authenticated === true`                                                                         |
| 产出     | 返回同一 token                                         | 新 `token` + `accessTokenInfo.refreshToken`                                                      |
| 有效期   | token 约 24h（README 记载）                            | authCode 一次性                                                                                  |

### 4.2 authCode 从哪来（浏览器 OAuth）

`example/browserOauth.ts`：puppeteer-extra + stealth 打开 `https://trade.thinkorswim.com/`，
在 `sws-gateway-nr.thinkorswim.com` 登录 iframe 中定位 `#loginIdInput`、`#continueBtn`、
`#passwordInput`，输入账密；拦截 `trade.thinkorswim.com/oauth?code=…` 的重定向请求、
`abort()` 阻止消费 code，从 URL 提取一次性 authCode。

### 4.3 现状风险（一年停更后最可能坏的地方）

1. **登录页 DOM 漂移**：iframe 域、元素 id 都可能改；该脚本无自愈能力（选择器写死、
   `waitForNavigation` 结果未 await、无超时/失败路径）。
2. **MFA/2FA 强制化**：Schwab 已逐步推行两步验证码，脚本没有处理 OTP 页的分支；
   真实账户大概率会被要求验证码或设备批准。**方案：改为"半人工"模式——浏览器打开、
   用户手工完成登录（含 MFA），脚本只负责截获 code**（这也是对协议最稳的跟随方式）。
3. **refreshToken 有价无市**：代码里 refreshToken 只存不用。网页前端实际会用它续期；
   需要黑盒确认刷新通道（推测走 `login` 或 HTTP `authapi.schwab.com` OAuth token 端点，
   待实测，列入黑盒测试 C 组）。
4. TDA 老通道（`userDomain: "TDA"`、`userCdi` 等字段）已随 TD Ameritrade 迁移完成而
   基本退场，Schwab 单通道是现实；但 login 响应里可能仍带遗留字段，解析需宽松。

## 6. 本地代理协议（WsJsonServer）

浏览器/其他进程 → 本地 `ws://localhost:8080`：

```jsonc
{ "request": "quotes", "args": ["ABNB","UBER"] }   // 注意: server 端 args 直接整体传参
{ "request": "authenticateWithAccessToken",
  "args": {"accessToken":"…","refreshToken":"…"} }
```

回程 `{request, args, response}` 按方法名多播；`dateReviver` 还原 ISO 日期。
代理端每个连接创建一个独立 `RealWsJsonClient`。
缺口：无鉴权、args 形状与 client 方法签名不完全一致（wsProxyClient 示例用
`quotes ["ABNB","UBER"]` 数组，而 relayIterable 直接把 args 当第一参数传，恰好数组
就是 symbols，成立但脆弱）、无错误码约定。
