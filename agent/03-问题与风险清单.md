## 4. 类型与 API 设计

- A1 所有响应统一为 `Record<string, unknown>`，19 个服务只有 request 类型没有
  response 类型收口（`RawPayloadResponseQuotesItem` 等定义了但没人用）。
- A2 `userProperties()` 返回 `{body}`，调用方需 `body.defaultAccountCode as string` 硬转。
- A3 `workingOrders` 的 handler 每次 new，不在 messageHandlers 注册表内（风格不一致）。
  （✅ task-14C：已注册并改 dispatchHandler 查表派发。）
- A4 `subscribeToAlertMessageHandler` 已实现却未接入 `RealWsJsonClient`/接口/代理（死代码）。
  （✅ task-14B：subscribeAlerts() 已接入，接口/mock/双向代理同步。）
- A5 `mockWsJsonClient` 与真实返回形态漂移（如 `orderChain` body `{}`）。
- A6 `wsJsonClientProxy.ALL_REQUESTS` 中 `optionChainQuotes` 重复出现两次。
- A7 `ensureConnected` 报 "Please call connect() first"，但根本不存在 `connect()`。

## 5. 服务端代理（WsJsonServer）

- S1 无鉴权：本地端口任何进程可完全操控交易会话。
- S2 `relayPromise` catch 后 `response: e`——Error 经 `JSON.stringify` 变 `{}`，错误全丢。
- S3 `args` 形状无 schema 校验，与 wsProxyClient 的数组传参方式耦合脆弱。

  协议漂移不可见）。
